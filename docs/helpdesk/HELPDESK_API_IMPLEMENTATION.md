# Implemented isolated Helpdesk API

**Current harness update (10/11/2026):** chat now requires login, supports account-scoped current conversation/history, and verifies current-room context. See the update at the end and [HELPDESK_HARNESS.md](HELPDESK_HARNESS.md); older guest-mode descriptions are historical.

Base: standalone PHP :8010/api/v1/helpdesk. Browser-facing bridge: /api/helpdesk. No existing server/public/index.php registration changed. Success/error envelopes follow H1; machine errors remain errors[0].code. This report describes implemented extensions to H1's proposed schema, which remains unchanged as preparation history.

## Endpoints

| Method/path under /api/v1/helpdesk | Behavior |
| --- | --- |
| POST /conversations | Create server-owned guest/authenticated conversation |
| POST /conversations/{uuid}/messages | Validated user message + bounded agent response |
| GET /conversations/{uuid}?limit=30&cursor=... | Owner-scoped ascending history, signed owner/conversation cursor, max 60 |
| POST /tickets | Explicitly confirm a stored proposal; persist real ticket/event |
| GET /tickets/{uuid} | Requester or explicitly allowed support only |
| GET /support/inbox | Authorized live support ID only, max 50 tickets |
| POST /tickets/{uuid}/status | Authorized support open→in_progress→resolved; resolved→open allowed |
| POST /conversations/{uuid}/operator | Authorized support activate/message/resume/resolve |
| GET /health (outside API base) | Minimal process liveness only; not model/DB readiness |

The browser bridge exposes only conversation create/messages/history and ticket create/read. It does NOT proxy the privileged support routes. A separate authorized operator client can access those PHP endpoints with a server-controlled bridge secret and real Bearer credentials; no human inbox UI is provided.

All protected PHP requests need X-Helpdesk-Bridge matching the server secret plus Origin matching HELPDESK_FRONTEND_ORIGIN. Guest identity uses X-Helpdesk-Session (64 random hex characters), generated by the bridge and stored HttpOnly in the browser; PHP persists only an HMAC owner key. The bridge credential is not an end-user credential. Authenticated requests instead validate Authorization: Bearer through live /auth/profile on every call, with no guest downgrade on failure. Claimed body roles, context.surface, booking IDs and demo personas grant no permissions.

~~~

Unknown fields, invalid UUIDs/JSON/context, nonblank limits and oversized bodies are rejected. Ticket category/description are taken from the stored proposal, not mutable confirmation fields. No public contact_verified, booking reference, role, SQL or tool field is accepted.

## Message success data

Preserves H1 conversationId/userMessageId/messageId/clientMessageId/role/createdAt/response/citations/reasonCode/answerKind/corpusVersion. response matches the widget text/mode/state/sources with optional actual room cards, ticketProposal and handoffStatus. A proposal contains id/category/description/suggestedDestination plus server metadata; it is not a ticket. Confirm success returns data.ticket, with committed ID, actual lifecycle and unclaimed assignment.

Policy answers have answerKind=rag and citations built only from retrieved applicable chunks. Catalog answers use answerKind=catalog and projected actual API results, no fake policy citations. Unsupported/safety responses have answerKind=abstention. Errors such as missing provider configuration are HTTP errors, not successful assistant replies.

Conversation states extend H1 bot/closed to bot_active/handoff_requested/human_pending/human_active/resolved. Capabilities now describe publicFaq, publicCatalog, tickets, humanHandoff and humanInbox along with false liveBooking/livePayment/liveRefund/businessActions. tickets=true means the feature exists, not that an unverified guest may create one. humanHandoff=true means requests can queue, not that an operator is online.

Existing H1 JSON schemas do not yet encode these ticket/catalog/state extensions. Runtime PHP strict validators and TypeScript response guards implement the current wire profile; consumers must use this implementation contract, not assume the historical schema certifies these new fields. No shared business response helper was changed.

## Authorization, idempotency and failures

Every conversation/message/ticket access verifies owner; missing and cross-owner both return 404. A random ID alone gives no access. Host role is not global ticket access. Support requires an explicit server allowlist AND live profile verification; the empty default disables it.

Message retries reuse clientMessageId and content; same key/different content gives 409. In-flight turns reserve a short lease; repeated keys/parallel turns return request_in_progress/conversation_busy. User/assistant pair, result and trace are committed together. Failed generations can be retried with the same key without appending duplicate messages. Create-conversation requests are NOT idempotent in this slice; the adapter avoids automatic creation retries. This is a documented difference from H1's optional creation-key proposal.

Ticket confirmation is duplicate-safe by immutable proposalId and conversation lock. Only explicit confirmed=true plus verified requester/contact persists it. Guests without external contact verification get 401 verified_contact_required; no email/SMS is sent or falsely verified. Ticket status transitions record actor and timestamps. Host destinations remain suggestions in an unclaimed support queue until a trusted ownership integration exists.

Common errors: 400 invalid_json/unknown_field/invalid_id; 401 authentication_required/verified_contact_required; 403 origin_denied; 404 resource_not_found; 409 idempotency_conflict/conversation_busy/invalid transition; 413 payload_too_large; 415 unsupported_media_type; 422 validation/tool/step limit; 429 rate_limited; 502 invalid_provider_response/ungrounded_response; 503 provider_not_configured/model_not_configured/tool_calling_disabled/storage_unavailable; 504 generation_timeout. JSON errors never expose SQL, stack traces or provider credentials.

Prompt injection cannot add tools/permissions; schema/allowlist checks execute server-side, live readers are absent, and final policy text must equal complete retrieved paragraphs. This bounds behavior but does not claim universal injection immunity. See [actual tests](AGENT_EVALUATION_REPORT.md).

# Cập nhật harness 10/11/2026

Chat HTTP hiện **bắt buộc đăng nhập** qua cookie HttpOnly ở Next bridge và Bearer được xác minh bằng backend profile tại PHP. Guest create/history/current/messages trả 401; các mô tả guest ở các phần trước được thay thế bởi yêu cầu này. `/health` vẫn public.

Endpoint mới `GET /api/v1/helpdesk/conversations/current` (BFF `GET /api/helpdesk/conversations/current`) không nhận query/owner ID. Success envelope hiện có bọc data `{conversation: Conversation|null, messages: Message[], nextCursor: null}`. Actor chỉ nhận pointer hội thoại hiện tại của chính tài khoản, ownership/expiry tiếp tục được kiểm tra. Không có chat thì conversation=null và messages=[]; lỗi storage/auth không bị đổi thành empty.

Create conversation chủ động cập nhật pointer trong Helpdesk-owned records. Message context `{surface,scope?:"catalog",roomId?:positive integer}` là UI hint, được đối chiếu public API trước khi model dùng. Hash idempotency gồm text và context. Không đổi payload booking hoặc API nghiệp vụ. Xem [harness](HELPDESK_HARNESS.md) cho state, resume và test.
