# Helpdesk API contract — proposed, unavailable today

Version 1.0.0 · 27 October 2026. No route or adapter is implemented. Exact current routes are in server/public/index.php; none has a Helpdesk prefix. Existing widget remains demo-only. [JSON schemas](HELPDESK_API_CONTRACT.schema.json) use JSON Schema 2020-12; validate the named $defs fragment per operation. UUID and date-time format assertions must be enabled, with semantic checks below.

## Proposed endpoint surface

| Operation | Method/path | Input schema fragment | Success schema fragment |
| --- | --- | --- | --- |
| Create chat | POST /api/v1/helpdesk/conversations | CreateConversationRequest; optional Idempotency-Key UUID header | CreateConversationSuccess, HTTP 201 |
| Continue / read authorized chat | GET /api/v1/helpdesk/conversations/{conversationId} | UUID path + HistoryQuery | HistorySuccess, HTTP 200 |
| Send message | POST /api/v1/helpdesk/conversations/{conversationId}/messages | UUID path + MessageRequest | MessageSuccess, HTTP 200 |
| Report unsupported/live/missing/conflicting question | Same messages endpoint | MessageRequest | MessageSuccess with response.state=unavailable and reasonCode |
| Report operational/authorization failure | Any endpoint | As above | Error fragment + corresponding HTTP status |

Continue by keeping the returned server conversation ID and sending to its messages endpoint; do not let callers select an arbitrary owner or reassign a conversation. There is no separate reporting/ticket endpoint: an unsupported question creates a normal abstention message and minimal reason telemetry. No claim that staff were notified.

All POST requests require application/json, UTF-8 JSON objects, strict unknown-field rejection, body <=8 KiB, and nonblank trimmed text <=1,000 UTF-16 code units (matching current JS length bound). Reject malformed JSON with 400 rather than accepting Core Request's current empty-array fallback. JSON Schema maxLength counts Unicode code points; the additional UTF-16 limit is an explicit server semantic rule. Reject client-supplied role, actor/user/Studio ownership, system prompt, tools or assistant answer. IDs are server-generated UUIDs, except clientMessageId/idempotency keys generated by the adapter.

The success and error wrappers retain Core ApiResponse conventions: status, numeric HTTP code, message, data OR errors. ApiResponse::error currently drops its errorCode parameter. Therefore Helpdesk machine errors MUST appear in errors[0].code (field empty for general errors), not a fictional top-level errorCode. This may be implemented in a module-only mapper in a future task; generic middleware errors also need normalization in the future adapter.

## Identity, permissions and guest proposal

Authenticated mode uses a real existing PHP Bearer JWT validated through active AuthMiddleware, which reloads the live user and role. The localStorage demo persona and context.surface are not authentication. Invalid/expired Bearer credentials return 401; do not silently downgrade to guest.

Public guests need a separately implemented server-managed session: cryptographically random opaque identifier in Secure, HttpOnly, SameSite=Lax cookie, short expiry (proposed 24h), server-side hashed session record and rotation. Do not expose that secret in JSON, URLs, logs or the LLM. Create guest session and conversation atomically; do not return an unusable conversation when persistence is unavailable. Guest access is a proposed prerequisite, not something existing AuthMiddleware already supports. A local CLI demo needs none of this.

For guest cookie POSTs, require Origin allowlist and CSRF token header tied to session; issue the token through a reviewed same-origin/BFF handshake, not in chat. Prefer a same-origin transport for this initial contract; cross-origin credential/CORS handling requires a separate design check. Guest routes require a new Helpdesk identity resolver, not unconditional existing AuthMiddleware. Rate-limit guest creation and messages by session/IP; don't trust a caller's IP header without a trusted-proxy configuration.

On every request, query conversation by ID AND server-derived owner/session; check expiry/state before loading messages or answering. Random IDs are not authorization. A missing or another owner's conversation returns identical 404 resource_not_found; absent credentials on a protected history/message request return 401. A Host can read only their own Helpdesk conversation, not all chats associated with their Studio. Admin access requires an explicitly granted support permission; current role alone gives none. Never accept client ownerId/role for authorization.

On login, logout, user change or guest expiry, discard adapter conversation state and fetch/create under the new identity. No automatic guest-to-account merge in v1. A booking-suspended customer retains support access under BP-04/28; security-locked accounts remain subject to real auth middleware. No private tools exist in H1, regardless of identity.

## Conversation and message semantics

A Conversation contains id, ownerMode, bot/closed state, connected mode, locale, createdAt/expiresAt and server capabilities. Current H1 capabilities permit approved public FAQ only; all live reads, financial queries, business actions, tickets and human handoff are false. An unavailable knowledge release produces 503 rather than publicFaq=true with an empty or unapproved corpus. Limits: <=60 stored messages including both roles; at most one in-flight turn per conversation. A generated user/assistant pair consumes two slots; overflow gives 409 conversation_limit. No fake welcome message need be persisted.

MessageRequest contains text, stable clientMessageId and optional context.surface. Server assigns role=user, userMessageId and timestamp, then returns assistant role, messageId, createdAt and response. Store exact returned IDs/timestamps; the existing hook currently generates local IDs and needs a later documented history enhancement if server history is exposed.

Idempotency key scope is (server owner, conversationId, clientMessageId). Repeat same normalized content returns the same completed answer, IDs and citations without another provider call. Same ID/different normalized content returns 409 idempotency_conflict. Reserve an in-flight key/turn atomically; return 409 request_in_progress with Retry-After for duplicate in-flight requests, and conversation_busy for a different turn. On provider failure retain recoverable turn state; retry with the same ID must resume/replace the failed attempt rather than append another user message. Commit completed assistant response/citations and idempotency result atomically. A failed provider attempt is not a successful answer. Create-chat Idempotency-Key similarly prevents duplicate creation for an existing owner; a client with no established guest session must establish identity before retry-safe creation.

A client abort/timeout does not roll back server work. Retry the same clientMessageId or read history; never generate a new key just because the response was lost. Current hook's manual re-send uses no persisted idempotency key; full retry/history reconciliation is a later integration change, documented rather than implemented here.

History is ascending by server sequence, limit default 30, max 60. Cursor is opaque, authenticated/signed and bound to owner+conversation+sequence, expires with conversation; clients cannot use offsets to bypass ownership. Return nextCursor=null at end. User messages have id, role=user, text, createdAt and clientMessageId. Assistant messages include WidgetResponse, citations and nullable reasonCode. Return no system prompts, tool traces, raw provider output or internal retrieval content. Retention/expiry is enforced server-side; inaccessible resources return 404, while an already-authorized known expired session may receive 410 conversation_expired without leaking other resources.

## Answer/citation semantics

MessageData includes conversationId, userMessageId, assistant messageId, echoed clientMessageId, role=assistant, createdAt, response, citations, reasonCode, answerKind and corpusVersion.

WidgetResponse preserves text, mode, state and sources compatible with HelpdeskResponse. This H1 wire profile deliberately omits optional cards and links; no booking/card/ticket payloads are available. Public source links are not invented. response.mode MUST be connected on a real network success, including connected deterministic FAQ; answerKind distinguishes faq, rag and abstention. Demo mode is only produced by the separate existing local demo transport. Never downgrade a network failure to mode=demo. The full enum remains in the shared response schema for adapter compatibility, but server semantic validation enforces this endpoint rule.

answered requires answerKind=faq or rag, reasonCode=null, 1–3 verified citations and matching sources (same order/title/reference, including policy version in reference). Every policy claim needs source coverage; sources are not merely decorative. Each citation contains id, documentId, chunkId, title, reference, documentVersion, corpusVersion, scope and nullable studioId. IDs/versions must match actual selected approved chunks. Model-supplied IDs must be checked; server constructs metadata, never arbitrary model citations. Platform scope requires studioId=null; studio scope requires an authorized resolved Studio ID.

unavailable requires answerKind=abstention and a ReasonCode. Typical unsupported/conflict/missing-live responses have empty citations/sources; partial policy guidance may cite only supported claims and clearly leave live data unanswered. unauthorized is reserved for message-level private-data refusal; HTTP identity failures still return 401/403 Error. human_handoff is in the existing widget type but MUST NOT be emitted in H1 because no handoff capability exists.

## Error/status table

| HTTP | Machine code examples | Behavior |
| --- | --- | --- |
| 400 | invalid_json, invalid_request, invalid_cursor | Reject before provider call |
| 401 | authentication_required, token_expired, guest_session_expired | No private output; reset/re-authenticate |
| 403 | account_locked, origin_denied, csrf_failed | Do not bypass live authentication/security checks |
| 404 | resource_not_found | Consistent missing/cross-owner response |
| 409 | idempotency_conflict, request_in_progress, conversation_busy, conversation_limit, conversation_closed | No duplicate messages/actions |
| 410 | conversation_expired | Only after ownership established |
| 413/415/422 | payload_too_large / unsupported_media_type / invalid_message | Bound body, JSON and whitespace/text |
| 429 | rate_limited | Retry-After, bounded retry, no model call |
| 500 | internal_error | Correlation header only; no internals |
| 502 | invalid_provider_response | Invalid structure/citations not returned as answer |
| 503 | knowledge_unavailable, provider_unavailable, conversation_store_unavailable | Explicit readiness failure |
| 504 | generation_timeout | Retry-safe message ID; no demo success fallback |

Add X-Request-Id (opaque), Cache-Control: no-store, safe JSON content type and Retry-After where relevant. No tokens, keys, payment details or raw exceptions in response errors. Array/text bounds in schema supplement auth and runtime semantic tests.

## Frontend adapter and future shared changes

Keep HelpdeskTransport.sendMessage(message, context?, {signal}?) → Promise<HelpdeskResponse>. A future PHP adapter internally holds a server conversation ID and stable retry keys, creates chat once, posts messages, validates JSON and semantics, and returns data.response. Preserve AbortSignal, sources and the 15-second hook deadline; server work budget should be shorter. transport.mode=connected reflects explicit configured network transport, not connection health; failures remain failures.

The existing transport interface cannot expose server history IDs directly. Adapter-owned history can be fetched securely, but displaying it needs a later hook/state integration. Identity-change reset, lost-response reconciliation, CSRF/BFF/JWT transport and readiness checks are future documented requirements; no widget edit or fake JWT bridge was made.

Shared router registration must be separately authorized in server/public/index.php: explicit POST create, POST messages and GET history routes, UUID validation, identity/ownership middleware and Helpdesk composition. Current numeric business-route patterns cannot be copied for UUIDs. Check OPTIONS route handling before browser integration. Conversation storage and cleanup require an isolated persistence design in that future slice; proposed endpoints cannot function simply by adding route names. No schema changes, ticket routes, new dependencies, deployment or actual API calls occur in H1.
